# 飞书内部应用：补录手卡配置中心

## 已确认的需求

- 仅公司内部使用，所有可使用应用的同事均可配置自己有编辑权限的表格。
- 同事从飞书应用打开配置页面，选择表格和手卡字段；日常仍点击多维表格行内的「补录手卡」按钮。
- 项目负责人会手动配置各表的按钮自动化，不要求程序创建飞书自动化。
- 共用现有服务器与手卡处理逻辑，不替换当前连接的飞书应用，不改视频流程。
- 必填 PID；产品名称可选。保留已上线的按 PID 缓存、查找/生成手卡、只回填当前行规则。

以上为项目负责人本次对话确认；下面实现细节根据代码，不代表真实飞书验收已完成。

## 入口与边界

网页应用入口：`https://<服务器地址>/feishu/handcard`。这是在飞书里打开的应用页面，不是多维表格侧边栏插件，也不是自动化市场连接器。

页面依次提供：飞书登录 → 粘贴 Base/wiki 链接 → 选择子表 → 选择 PID/名称/手卡/状态列 → 保存 → 显示按钮请求示例。

首版这四项均只支持**文本列**。PID 不接受数字列，以免精度损失；名称和状态列可不选。手卡链接以文本写回，与原处理器一致，不承诺支持超链接类型、公式或附件列。无权限、普通电子表格、字段类型不兼容时明确拒绝，不自动改表结构。

读取与保存配置不会调用出海匠或 AI，也不会创建手卡；只有点击原行内按钮才触发原业务流程。

## 两个应用的分工

新应用只用于同事身份登录、读取其可编辑表格、保存本系统字段映射。

原应用继续执行按钮请求、读写当前行、访问原模板和手卡目录。**不能把新 App ID/Secret 覆盖到原 `feishu_settings`。** 新旧应用凭证不互换，用户 open_id 按新应用记录。

保存前分别检查登录人的 Base 编辑权限和原执行应用的 Base 编辑权限，并读取双方可见字段的交集。高级权限/行级规则可能仍限制某些行的写回，必须用真实按钮验收；读字段成功不是完整写回成功。

## 服务器配置（均不得填入客户端代码或提交密钥）

在服务器私有 `.env` 设置下列可选变量，由 Compose 传入应用容器；全部配齐才启用登录。

| 变量 | 用途 |
| --- | --- |
| `FEISHU_HANDCARD_APP_ID` | 新内部配置应用的 App ID |
| `FEISHU_HANDCARD_APP_SECRET` | 新应用密钥，仅服务器保存 |
| `FEISHU_HANDCARD_TENANT_KEY` | 本公司企业编号，登录用户 tenant_key 必须完全匹配；部署时用已授权的企业信息接口或管理员确认，不能从第一次登录自动接受 |
| `FEISHU_HANDCARD_ORIGIN` | 公网 HTTPS origin，不含路径、查询参数；例如 `https://<服务器地址>` |

不复用后台管理员密码或自动化共享密钥作为同事登录凭证。现有 webhook 密钥只由配置按钮的负责人掌握，配置页面不回显。

会话加密复用现有 `.data/secret.key`，用户 access token 加密后存入 `feishu_handcard_sessions`，浏览器只收到随机会话标识；会话标识在数据库中存 SHA-256 摘要。有效期取接口 expires_in 减 30 秒，最长 2 小时。无需 offline_access，不存刷新令牌；过期重新登录。登录时清理过期会话，不增加定时扫描任务。

## 飞书开放平台一次性设置

1. 在用户指定的内部自建应用中启用「网页应用」，电脑/移动端入口填 `/feishu/handcard` 的完整 HTTPS 地址。保留应用已有机器人等能力。
2. 在安全设置里加入精确重定向 URL：`https://<服务器地址>/feishu/handcard/auth/callback`。入口域名及相关安全域名须符合该应用控制台实际校验要求；IP 地址是否被接受，需现场验证，必要时使用已有域名，不能仅凭 HTTPS 可访问断言可发布。
3. 申请用户身份权限 `bitable:app`（读取表格字段和调用编辑权限检查）与 `wiki:wiki:readonly`（解析知识库链接）。本实现不会用用户 token 调用修改飞书数据的 API。权限校验接口可选择更细的等效权限，若未来改为最小 granular scopes，应同步调整 `auth.ts` 和验收。
4. 应用可用范围设为内部全体员工，创建版本并按企业审批规则发布。若当前账号无开发/发布权限，需要负责人操作。
5. 给原负责执行手卡的应用授权目标多维表格读写；原模板和手卡文件夹权限继续保持。新应用用用户身份读取，不要把“新应用能登录”当作“原应用能回填”。

仅 App ID/Secret 无法设置网页入口、审批权限或代替管理员发布。本次代码不自动更改上述控制台设置。

## 同事及负责人操作

同事：飞书工作台打开应用 → 飞书登录 → 粘贴多维表格/知识库链接 → 选择子表 → 读取字段 → 选择四项 → 保存。

负责人：设置行内按钮自动化，发送 POST 到现有 `/api/feishu/automation`，使用原认证请求头 `X-Feishu-Automation-Secret`。Body：

```json
{
  "appToken": "配置页面显示的真实Base编号",
  "tableId": "配置页面显示的数据表编号",
  "recordId": "插入飞书触发记录的记录ID变量"
}
```

`recordId` 必须是动态变量。不要继续发送旧的 `fieldMap`，否则旧请求覆盖页面保存的字段选择；也不要把视频链接或整行数据一起送入这个手卡请求。

在测试行填 PID，产品名称可留空；点击按钮，检查产品手卡列及可选状态列。HTTP 返回 accepted 只表示已接收，不表示文档创建完成。

## 实现与隔离

- `app/feishu/handcard/`：页面、OAuth login/callback、配置 API。
- `lib/feishu/handcard-app/core.ts`：固定入口配置、官方链接、字段类型、同源校验。
- `auth.ts`：OAuth v3 + PKCE + state、内部企业限制、加密持久会话。
- `tables.ts`：wiki 解析、双方权限/字段检查、分页完整性、带版本冲突检测的事务保存。
- `http.ts`：8 KB 请求限制、每用户/登录来源 20 次/分钟（单进程）限制、固定安全错误。
- 新建两张表：`feishu_handcard_sessions`、`feishu_handcard_config_audit`。只增表，不改历史记录/资料；审计存操作人、旧新映射、时间，不存密钥。
- 保存只更新四个手卡映射项，保留视频映射及其别名；清理这四项旧自定义别名，避免旧别名干扰新选择。原处理器内置别名兼容规则不变。
- 不列出全部公司表格配置；只在当前用户再次通过权限检查后读取指定表的配置。无配置删除入口。
- 原自动化路由新增：读取已保存的映射后再补齐当前行的 PID/名称，失败状态使用同一映射。原处理器对空状态列不再写入空字段。
- `proxy.ts` 只对准确的新路径交由飞书会话认证，不开放其他后台路由或 Server Actions；生产新入口强制 HTTPS、禁止第三方 iframe 嵌入；不使用跨域 iframe 承载页面。

## 验证与发布边界

本地离线测试覆盖：路由隔离、内部身份限制、state/PKCE、会话摘要/加密、过期和退出、跨站/超大请求、权限撤回、字段变化、分页异常、并发修改冲突、视频字段保留、空状态列、按钮自定义映射补齐。

2026-09-19 本地结果：81 项手卡/应用/登录相关检查、173 项视频与验证流程检查、19 项部署防护检查通过（合计 273 项）；TypeScript、限定范围 ESLint、生产构建通过。本地浏览器用模拟数据验证选择表、选择字段、名称/状态可选、保存提示、退出，未连接真实飞书数据。

本机无 Docker/MySQL，新增真实 MySQL 用例当前跳过，已接入 CI 的隔离数据库步骤，尚未推送运行。另有 `feishu-product-card-mapping.test.mjs` 的 2 项旧测试无法解析其测试加载器里的 `@/lib/db/pool`，已在未改动的 357e8cb 基线复现；未将这两项算为通过，未修改其旧加载器。当前功能**未提交、未推送、未部署、未发布飞书应用**。

真实发布前必须完成：

- 隔离 MySQL 执行新增表及事务测试（单元测试不等于真实数据库并发）。
- 飞书控制台配置、实际 OAuth 登录及公司 tenant_key 验证。
- 普通同事可配置自己可编辑的表；无权表不可配置。
- 一张有产品名称及一张仅有 PID 的测试行，按钮回填成功；没有视频任务被误触发。
- 两人同时修改同表，过期页面保存收到冲突提示；原手卡和视频流程回归。

回退：移除/清空四个新环境变量即可禁用新应用登录；已保存映射仍会影响原按钮，不会自动撤销。需要撤销时，负责人按审计记录在原后台恢复对应四项，保留视频配置。数据库增量表无需删除。
